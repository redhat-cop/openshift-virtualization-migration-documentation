This page is a **run sheet** for a Services Consultant on a **customer bring-your-own** environment. Target: finish your first Migration Factory sitting in about **four hours**, including environment setup. It is not a second copy of the journey — follow the steps here; open the linked journey pages when you need the full procedure.

== Formats

* **Web:** this Antora page (always current).
* **PDF:** use **Export PDF** at the top. The PDF keeps the same ordered steps and the same links into the documentation on this site. There is no separate offline PDF artifact to download.

== What you will finish

With basic OpenShift Virtualization knowledge (Ansible and MTV may be new):

* Confirm the customer environment is ready for Migration Factory (Gate 0).
* Stand up Migration Factory on that environment (inventory → validate → seed).
* Migrate **one** VM from **VMware** to **OpenShift Virtualization** using **MTV + AAP + Migration Factory**.
* Validate: MTV plan **Succeeded**, VM **Running**, guest has an IP, **ping** works, and an **app check** you define when ping is not enough.

== Which guest and plan type?

Migration Factory and MTV support more than one guest OS and plan type. For a **first** sitting, use a **cold** plan (source powered off). Cold finishes in one MTV **Start** and is easier to reason about than warm (precopy + later cutover).

Pick **one** of these recommended first paths:

[cols="1,2,2"]
|===
| Path | Guest | Plan

| A (default)
| RHEL 8 or RHEL 9
| Cold

| B
| Windows Server (supported by MTV for your version)
| Cold
|===

Same factory steps for A and B. Differences are guest prep, how you prove the app after cutover, and MTV/OS prerequisites (VMware Tools / virtio / guest agent). Follow link:https://docs.redhat.com/en/documentation/migration_toolkit_for_virtualization/[MTV documentation] for guest OS support on your MTV version.

=== Other combinations (after the first sitting)

[cols="1,2"]
|===
| Need | Where to go

| Warm migration (source stays up until cutover)
| Set `type: warm` on the wave (xref:journey:prepare-migration-wave.adoc[Defining a migration wave]), then **Cutover** in xref:journey:execute-migration.adoc[Migrating VMs]. Budget extra time for precopy and cutover.

| RHV / other sources
| Same journey after the provider matches the source; see xref:journey:prerequisites.adoc[Prerequisites] and xref:journey:create-providers.adoc[Configure providers].

| Multi-VM wave
| Same wave page with more `vms` or `folders`; not the goal of this first four-hour sitting.
|===

== Estimated duration (~4 hours)

Use this to plan the engagement. Disk size, network, and how complete the platform already is will move the clock; Gate 0 failures usually cost more than the migration itself.

[cols="1,1,3"]
|===
| Phase | Budget | Focus

| Access, pick VM, Gate 0
| ~45 min
| Versions, one guest (RHEL or Windows), pass every Gate 0 check.

| Prepare + seed
| ~75 min
| Inventory → validate → seed AAP.

| Providers + maps
| ~30 min
| One VMware→OpenShift pair; maps **Ready**.

| Guest prep + wave + migrate
| ~60–90 min
| Power off (cold), one-VM plan, MTV **Start** → **Succeeded**.

| Validate + feedback
| ~30 min
| Start VM, IP, ping, app check if needed; xref:support:channels.adoc[Support] if blocked.
|===

== Suggested steps

Complete these in order. Do not skip Gate 0.

. Confirm access and version floors, then pick the RHEL or Windows VM.
. Pass **platform** Gate 0 (OpenShift Virtualization, MTV, AAP reachability, EE). Skip the inventory checkbox until the inventory file exists.
. Finish prepare: inventory → re-check the **inventory** Gate 0 item → xref:journey:validate-environment.adoc[Validate your environment] → xref:journey:seed-aap.adoc[seed AAP].
. Configure providers, then storage and network maps.
. Prepare the guest, power it off (cold), define a one-VM cold wave, start the plan in MTV, wait for **Succeeded**.
. Start the VM on OpenShift Virtualization, confirm IP, ping, then your app check if ping is not enough.
. Send feedback through xref:support:channels.adoc[Support] if something blocked you.

== Assumptions

* **Audience:** Services Consultant; OpenShift Virtualization basics; may be new to AAP and MTV.
* **Environment:** Customer BYO (no shared lab for this guide).
* **Source:** VMware vSphere via **vCenter** or a **standalone ESXi** host (MTV 2.6+ supports Endpoint type **ESXi** / `settings.sdkEndpoint: esxi`). You need one RHEL or Windows VM you may power off for a cold plan. If you only reach the hypervisor through a bastion, run Gate 0 `oc`/`curl` checks from that bastion (or any host that can reach the OpenShift API, AAP, and the ESXi/vCenter SDK URL).
* **VDDK:** Build and set a VDDK init image on the VMware provider before the first cold plan (xref:journey:configure-inventory.adoc[Configure the inventory] — `vddk.image`). Without it, cold copy on standalone ESXi often fails in **ConvertGuest** (`nbdkit` / HTTP range not supported), and `skipGuestConversion` still requires VDDK for raw copy. Use an image **you** are entitled to build — not an internal RHDP/demo tag.
* **Destination:** OpenShift cluster with OpenShift Virtualization and MTV already installed. Confirm `oc whoami --show-server` is **that** cluster — not a leftover workshop kubeconfig on your laptop.
* **Automation:** Ansible Automation Platform available (existing or deployed as part of prepare). On AAP 2.5+, the controller REST API is under `/api/controller/v2/` (not `/api/v2/`).

Version floors from the enablement story (confirm against the customer platform and current collection support):

* vSphere 7.0+
* OpenShift 4.18+
* AAP 2.5+
* MTV 2.6+

Full access and credential checklist: xref:journey:prerequisites.adoc[Prerequisites].

== Pick the VM

Choose **one** VM (RHEL or Windows) that:

* You may power off for a cold migration.
* Has a stable name you will put in the wave request.
* Can answer **ping** from a host you will use after cutover (or will after you start it on OpenShift Virtualization).
* Has an **app check** you can describe if ping alone is not enough for the customer (HTTP URL, Windows service name, SSH command, and so on).
* Is not the only path to a critical production service for this sitting.

On vSphere, note the VM name (and folder/path if you will identify it that way). You will power it off before you start the plan.

== Gate 0 — ready for Migration Factory?

Pass **every** checkbox before you continue. If any item fails, stop, fix it, and re-check. Do not seed to paper over a missing operator. This gate matches xref:journey:validate-environment.adoc[Validate your environment]; the commands below are a CLI path to the same checks.

=== Checklist

Platform (do these first; no inventory file required yet):

* [ ] `oc` reaches the **destination** cluster (correct context / API URL)
* [ ] OpenShift Virtualization operator Succeeded; VM APIs exist
* [ ] MTV operator Succeeded; *Migration* appears in the OpenShift console
* [ ] You can log in to AAP (URL you will put in the inventory as `aap_hostname`)
* [ ] Execution environment pull works for the Migration Factory EE image (laptop Podman **or** AAP registry credential)

After xref:journey:configure-inventory.adoc[Building your inventory]:

* [ ] Inventory has the three groups, no leftover `changeme`, and `vm_sources` names match hosts

=== How to check each item

==== OpenShift API and context

Confirm you are talking to the customer destination before any operator checks:

[,shell]
----
oc whoami
oc whoami --show-server
----

Expect a successful identity and an API URL for **this** engagement. If DNS fails, the request times out, or the URL is a leftover workshop/sandbox, fix kubeconfig / `oc login` and stop — do not interpret empty `oc get csv` greps as “operators missing.”

==== OpenShift Virtualization

Logged in to the destination cluster:

[,shell]
----
oc get csv -A | grep -iE 'virt|kubevirt|openshift-virtualization'
oc api-resources | grep -i kubevirt
----

Expect a Succeeded CSV (or equivalent) and VirtualMachine-related API resources.

==== MTV

[,shell]
----
oc get csv -A | grep -iE 'mtv|forklift|migration-toolkit'
oc get forkliftcontrollers.forklift.konveyor.io -A
----

Expect a Succeeded CSV and a Forklift controller. In the console, confirm *Migration* lists Providers and Plans.

==== AAP login

Replace the hostname with your `aap_hostname`:

[,shell]
----
curl -kI "https://<aap_hostname>/"
----

Expect an HTTP response (not a connection error). Then open the same URL in a browser and sign in with the account from the inventory.

On AAP 2.5+, you can also confirm the controller API (path is `/api/controller/v2`, not `/api/v2`):

[,shell]
----
curl -sk -u '<user>:<password>' "https://<aap_hostname>/api/controller/v2/ping/"
----

Expect JSON that includes a `version` field.

==== Inventory file

Run this only **after** you have copied and filled the inventory from the collection sample (xref:journey:configure-inventory.adoc[Building your inventory]). From the directory that holds your inventory file:

[,shell]
----
grep -n 'changeme' inventory.yml || echo 'No changeme placeholders'
grep -E '^\s*(migration_aap|migration_clusters|vm_sources):' inventory.yml
----

Expect no `changeme` values you still need to replace, and the three group names present. Confirm by eye that every name under each cluster's `vm_sources` exists as a `vm_sources` host.

==== Execution environment

Prefer the path you will actually use for seed:

* **Seed / jobs from AAP:** configure the registry credential on AAP and confirm a test job can pull `quay.io/redhat-cop/openshift-virtualization-migration-ee:latest`. That satisfies this Gate 0 item without local Podman.
* **Laptop Podman (optional):** on macOS, ensure the Podman machine is running (`podman machine start` if the socket connection is refused), then:

[,shell]
----
podman login quay.io/redhat-cop
podman pull quay.io/redhat-cop/openshift-virtualization-migration-ee:latest
----

Quay credentials for that repository come from the Bitwarden collection *Migration Factory*. Create or request your Red Hat Bitwarden account with link:https://redhathub.service-now.com/hub?id=kb_article&sysparm_article=KB0010984&table=kb_knowledge&searchTerm=bitwarden[KB0010984] and link:https://redhathub.service-now.com/hub?id=request_help[Request help] if needed, then join the `migration-factory` Google Group. Details: xref:journey:migration-factory-prerequisites.adoc[Migration Factory prerequisites].

See xref:journey:source-collection.adoc[Sourcing the collection and execution environment].

When every **platform** box is checked, continue to prepare. After the inventory file exists, check the inventory box, then xref:journey:validate-environment.adoc[Validate your environment], then xref:journey:seed-aap.adoc[Seeding Ansible Automation Platform].

== Run the quick start

=== 1. Prepare the environment

Work through xref:journey:setup-environment.adoc[Preparing your environment] in order, stopping after validate:

. xref:journey:prerequisites.adoc[Prerequisites]
. xref:journey:migration-factory-prerequisites.adoc[Migration Factory prerequisites] (only if you still seed or install AAP from a laptop)
. xref:journey:source-collection.adoc[Sourcing the collection and execution environment]
. xref:journey:confirm-openshift-ready.adoc[OpenShift] — Virtualization and MTV already installed
. xref:journey:setup-aap-yourself.adoc[Ansible Automation Platform] **or** xref:journey:setup-existing-ocp.adoc[Deploying Ansible Automation Platform] if AAP is not installed yet
. xref:journey:configure-inventory.adoc[Building your inventory]
. xref:journey:validate-environment.adoc[Validate your environment] — Gate 0 again on the finished inventory

=== 2. Seed Ansible Automation Platform

. Put Quay pull credentials (Bitwarden *Migration Factory*) on the `migration_aap` host as `aap_execution_environment_username` / `aap_execution_environment_password`.
. On **AAP 2.5+**, mint a gateway token and set `aap_token` on `migration_aap` (do not rely on `/api/v2/tokens/` — it 404s). See xref:journey:seed-aap.adoc[Seeding Ansible Automation Platform].
. Run the seed playbook from a host that reaches AAP (bastion is fine). If `EE:latest` lacks `vmf_seed_aap`, mount the **v2** git checkout into the EE as shown on the seed page.
. In AAP, confirm the Migration Factory templates exist:
  **MTV Provider**, **MTV Maps**, **MTV Plans**, and **MTV Migrate**.
. Open *Jobs* after later steps — you will use that list as proof the sitting used AAP (not only a local `ansible-navigator` run).

=== 3. Providers and maps (AAP job templates)

After seed, run these steps from **AAP** (*Automation Execution* → *Templates*). The Quick Start sitting is proven by **successful AAP jobs** (Provider → Maps → Plans) plus MTV **Start**. Lab validation also confirmed `ansible-navigator` can create Plans when the v2 collection is mounted into the EE, but that is a debug/bootstrap path — do not skip AAP for the consultant run sheet.

[IMPORTANT]
.Execution environment must include the v2 roles
====
`quay.io/redhat-cop/openshift-virtualization-migration-ee:latest` may ship an older collection **without** `mtv_provider` / `mtv_maps` / `mtv_plans`. Before the first Provider launch, confirm the EE used by the Migration Factory templates can resolve those roles (or rebuild/point the AAP execution environment at an image that includes the **v2** collection). If a Provider job fails with `role ... mtv_provider was not found`, fix the EE first.
====

. Confirm inventory hosts and credentials exist: source host in `vm_sources`, target in `migration_clusters`, plus **Migration Factory - Source Environment** and **Migration Factory - Target Environment** credentials. On launch, attach both credentials when the template asks.
. Put VDDK on the source inventory host (`vddk.image`, and registry username/password if the image is private). Create a matching docker-registry pull secret in `openshift-mtv` if needed. See xref:journey:configure-inventory.adoc[Configure the inventory].
. For **standalone ESXi**, pass Provider extra vars so MTV uses the ESXi endpoint and VDDK init image:

.provider-extra-vars.yml
[source,yaml]
----
source_name: <vm_sources host name>      # e.g. esxi-lab
target_name: <migration_clusters host>  # e.g. ocp-lab
mtv_provider_provider_override:
  settings:
    sdkEndpoint: esxi
    vddkInitImage: registry.example.com/vddk:8.0   # image you are entitled to build
----

. Launch **OpenShift Virtualization Migration - MTV Provider**. Wait until the AAP job is **Successful** and the Provider is green in MTV.

image::journey:openshift-mtv-providers.png[MTV Providers with a valid source]

. Launch **OpenShift Virtualization Migration - MTV Maps** with survey/extra vars `source_name` and `target_name` (same inventory host names). Wait until the job is **Successful** and both NetworkMap and StorageMap are **Ready**.

image::journey:openshift-mtv-networkmaps.png[MTV NetworkMaps Ready]

Full procedure: xref:journey:create-providers.adoc[Configure providers], xref:journey:create-maps.adoc[Configure storage and network maps].

=== 4. Prepare the guest for a cold plan

. xref:journey:prepare-vms.adoc[Preparing VMs for migration] — maintenance window; VMware Tools (and Windows virtio / guest drivers as required by MTV).
. On vSphere / ESXi, **power off** the VM. Cold plans expect the source off for the cutover sitting.

=== 5. Define a one-VM cold wave (AAP MTV Plans)

. xref:journey:prepare-migration-wave.adoc[Defining a migration wave]
. In AAP, launch **OpenShift Virtualization Migration - MTV Plans**.
. Attach the Source + Target credentials. Set `source_name` / `target_name` (inventory host names) **and** the wave request (MTV names):

.quick-start-wave.yml
[source,yaml]
----
source_name: <vm_sources host name>
target_name: <migration_clusters host>
mtv_plans_migration_request:
  source: <mtv-provider-name>           # RFC 1123 form after Configure providers
  destination: host
  target_namespace: <project-for-vms>
  network_map: <source>-host            # or the names from Create maps
  storage_map: <source>-host
  verify_plans_ready: true
  plan_name: quickstart-aap-cold-01
  type: cold
  plan_overrides:
    preserveStaticIPs: false            # avoid warn when mapping to pod network
  vms:
    - name: <vm-name>
----

. Wait until the AAP job is **Successful**. Confirm the Plan CR is **Ready** in *Migration* → *Plans for virtualization*.

image::journey:openshift-mtv-plans.png[MTV Plans Ready]

[NOTE]
====
Survey `source_name` / `target_name` are inventory host names. Provider and map names in `mtv_plans_migration_request` are MTV names. See the wave page if those disagree.
====

=== 6. Start the migration in MTV

. xref:journey:execute-migration.adoc[Migrating VMs]
. In the OpenShift console, open the **Ready** plan → **Start**. That creates the Migration CR and copies disks. Cold finishes in the same run (no separate cutover).
. Optional: launch **OpenShift Virtualization Migration - MTV Migrate** with `source_name`, `target_name`, `mtv_migrate_plan_name`, and `mtv_migrate_plan_namespace`. Attach Source + Target credentials. Treat console **Start** as the cutover you rely on for this guide; confirm in the job log whether your collection version also creates the Migration CR.

image::journey:openshift-mtv-plan-virtual-machines.png[MTV plan Virtual Machines tab while running]

. In AAP *Jobs*, you should see successful **Provider**, **Maps**, and **Plans** (and optionally **Migrate**). Wait until the plan is **Succeeded** in MTV.

image::journey:openshift-mtv-completed-plan.png[MTV plan Succeeded]

=== 7. Validate

. xref:journey:verify-migration.adoc[Verifying a migration]
. Plan status **Succeeded**.
. Open the VirtualMachine in `target_namespace`. MTV leaves it **Stopped** — *Actions* → *Start* → wait until **Running**.

image::journey:openshift-migrated-vm.png[Migrated virtual machine Running]

. Confirm the guest has an IP (console, guest agent, or `oc` / VM details), then ping it from a host that can reach that address:
+
[,shell]
----
oc get vmi -n <target-namespace>
ping -c 3 <guest-ip>
----
+
Success on **ping** means the NIC and route you mapped are good enough for connectivity.

. **App check:** if ping is enough for this engagement, you are done with validation. If the customer needs proof the workload is up, run an app check **you define** for that VM — for example:
+
--
* RHEL: SSH and a service or HTTP check (`curl -I http://<guest-ip>/`, `systemctl is-active <service>`).
* Windows: RDP or WinRM reachability, or confirm a named service is running inside the guest.
* Any guest: the customer's own smoke test written down before you start the plan.
--
+
Record what you ran and the result. If ping fails, fix network map / NAD / firewall before you treat an app check as meaningful.

=== 8. Close the sitting (optional)

. xref:journey:close-migration-wave.adoc[Closing the migration wave] and xref:journey:archive-plan.adoc[Archiving the plan] when the customer process requires it.

== Done when

* [ ] Gate 0 passed before seed
* [ ] AAP jobs **Successful** for **MTV Provider**, **MTV Maps**, and **MTV Plans** (visible under *Jobs*)
* [ ] Plan **Start**ed from the OpenShift console (not the AAP Migrate template)
* [ ] One VMware VM (RHEL or Windows) cold-migrated via MTV + AAP + Migration Factory

* [ ] App check done (your definition), or documented that ping was enough for this sitting

== Troubleshooting

Work the symptom that matches, then use the linked journey page for the long procedure.

=== Cannot reach the OpenShift API / wrong cluster

. Run `oc whoami` and `oc whoami --show-server`.
. If you see DNS errors, timeouts, or a workshop/sandbox URL that is not this customer, `oc login` to the destination (or select the correct kube context) and re-check.
. Only then re-run the Gate 0 Virtualization and MTV commands. Empty greps on a dead API are not proof that operators are missing.

=== Operator or MTV menu missing

. Confirm you are on the destination cluster (`oc whoami --show-server`, `oc whoami --show-console`).
. Re-run the Gate 0 OpenShift Virtualization and MTV commands.
. In the console: *Operators* → *Installed Operators* — both must be Succeeded.
. If APIs are missing, install or repair the operators before seed. See xref:journey:confirm-openshift-ready.adoc[OpenShift].

=== Seed fails or EE will not pull

. Prefer proving EE pull via the AAP registry credential if jobs run from AAP.
. On a laptop: if Podman reports the socket connection refused, start the Podman machine, then retry `podman pull` for `quay.io/redhat-cop/openshift-virtualization-migration-ee:latest`.
. Quay unauthorized — load credentials from Bitwarden *Migration Factory* (xref:journey:migration-factory-prerequisites.adoc[Migration Factory prerequisites]).
. `Failed to get token` / 404 — use gateway `aap_token` on AAP 2.5+ (xref:journey:seed-aap.adoc[Seeding Ansible Automation Platform]).
. `vmf_seed_aap could not be found` — mount the v2 collection into the EE (same seed page).
. Re-check inventory: no `changeme`, AAP URL and auth correct.
. Read the seed job log in AAP or the navigator output; fix the first hard error (auth, project sync, EE), then re-run. See xref:journey:seed-aap.adoc[Seeding Ansible Automation Platform] and xref:journey:source-collection.adoc[Sourcing the collection and execution environment].

=== Provider not green

. For **standalone ESXi**, the Provider must use Endpoint type **ESXi** (`settings.sdkEndpoint: esxi`) and URL `https://<esxi-host>/sdk`. With Migration Factory templates, pass that via `mtv_provider_provider_override` if the inventory only has `host` + `sdk_endpoint`.
. Confirm the OpenShift **nodes** (not only your bastion) can reach the ESXi/vCenter SDK URL on 443.
. Confirm the AAP **MTV Provider** job used the right `source_name` / `target_name` inventory hosts and attached the Source + Target credentials.
. If the AAP job fails creating the provider secret with `secrets.forklift.konveyor` / webhook EOF, check `forklift-api` logs in `openshift-mtv`. On some MTV 5.0 builds the secret admitter **panics** (nil URL) when a labeled provider secret is created before the Provider CR exists — `failurePolicy: Ignore` is not enough because the API still returns 500. Backup and temporarily **delete** `validatingwebhookconfiguration/forklift-api-secrets`, re-launch **MTV Provider**, then restore the webhook from the backup.
. In MTV: *Providers for virtualization* — open the provider and read the status message (URL, credentials, VDDK).
. Fix inventory credentials or network path to vSphere, then re-launch the provider template. See xref:journey:create-providers.adoc[Configure providers].

=== AAP job: role mtv_provider / mtv_maps / mtv_plans not found

. The Migration Factory execution environment image is older than the **v2** project playbooks. Point the AAP EE at an image that includes those roles (or rebuild the EE with the v2 collection) and re-launch.

=== Plan never Ready

. Confirm maps for that pair are **Ready** (xref:journey:create-maps.adoc[Configure storage and network maps]).
. Confirm the VM name (or path) exists on the source and matches `mtv_plans_migration_request`.
. Confirm provider names in the request are MTV names, not only inventory host names.
. If the plan shows **VDDKInitImageUnavailable** / **VDDKInitImageNotReady**, set `spec.settings.vddkInitImage` on the source provider and a matching registry pull secret in `openshift-mtv` (and ensure cluster nodes can pull that image). Re-check until the plan is **Ready**.
. Re-launch **MTV Plans** after fixes. See xref:journey:prepare-migration-wave.adoc[Defining a migration wave].

=== ConvertGuest fails (range / nbdkit) or VDDK required

. Open the plan → failed VM → **ConvertGuest** (or importer) pod logs. On standalone ESXi without VDDK, a common message is that the server does not support HTTP range requests.
. Set a VDDK init image on the provider and a pull secret; do **not** rely on `skipGuestConversion` alone — raw copy still requires VDDK.
. Delete the failed Migration/Plan (and leftover PVCs in the target namespace if needed), power the source VM off again, recreate the cold plan, **Start** again.
. Customer-built VDDK tooling: link:https://github.com/redhat-cop/openshift-virtualization-vmware-vddk[openshift-virtualization-vmware-vddk]. Inventory shape: xref:journey:configure-inventory.adoc[Configure the inventory].

=== AAP Migrate job green but disks never move

. Confirm you already **Start**ed the Ready plan in the OpenShift console (*Migration* → *Plans for virtualization*), or that your collection’s Migrate playbook creates a Migration CR (check the job stdout).
. If the launch form asks for `mtv_migrate_plan_name` / `mtv_migrate_plan_namespace`, set them to the Plan you created; missing vars prevent the job from starting.
. See xref:journey:execute-migration.adoc[Migrating VMs].

=== Plan Succeeded but VM missing or wrong project

. Open the plan and note `target_namespace`.
. In *Virtualization* → *VirtualMachines*, select that project (not only `openshift-mtv`).
. See xref:journey:verify-migration.adoc[Verifying a migration].

=== VM Running but ping or app check fails

. Confirm the guest has an IP (`oc get vmi -n <target-namespace>` or console).
. Confirm your ping/app-check host can route to that subnet (NAD, NetworkMap, firewall, NSG).
. Inside the guest, confirm firewall allows ICMP or your app port.
. Revisit xref:journey:create-maps.adoc[Configure storage and network maps] if the wrong network was mapped.
